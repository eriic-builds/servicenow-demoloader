# SN DemoLoader

Use a saved config library, one chat front door, reviewed plans, separately approved deterministic execution and durable outcomes. This Windows skill includes a versioned local installer; unfinished content and revision features are not implied by installation.

## Authoring rule: make the audience's world believable

The audience should recognize their own working world in the records. Never put "demo", "synthetic", "sample data", "fake", "fictional", "for demonstration only", test-data labels, prefixes or equivalent disclaimers into audience-visible generated data: titles, article bodies, incident descriptions, comments, work notes, emails, chat messages, attachments, filenames, screenshots or search snippets. Removing the label is not enough: use coherent people, plausible situations, useful detail and natural operational language. Do not write authoring directions such as "do not invent a policy" into the record itself.

Keep generated-data provenance, scenario boundaries, approval state, ownership IDs and cleanup/recovery markers only in internal operational manifests/journals and technical metadata, outside the visible narrative. Keep technical tracking required for idempotency; do not strip source audit history or ownership controls. Internal tool/skill names may still identify the tool. Never claim these authored scenarios are evidence of actual customer activity or invent real customer policies/commitments as facts. Explain provenance honestly to the operator when needed without inserting immersion-breaking labels into the audience's records. This does not authorize rewriting existing source records without the required source-change approval.

Before preparing a write, review only the audience-visible fields and attachments for these labels and for awkward meta-instructions. Keep internal metadata outside that text. Apply this same rule to the first content pack and subsequent incident/Knowledge engines.

Requester-submitted incident descriptions use the named caller's first-person voice: "I", "my" and natural descriptions of what they tried and need next, not "Avery did" or a service-desk narrator speaking about the caller. Technician work notes retain the actual technician perspective when appropriate. Caller voice affects authored text only; it never changes the authenticated audit actor, spoofs sys_created_by or claims the person actually submitted the record.

## Incident and Knowledge article creation

The selected-profile fixed content engine supports one incident and/or one new Knowledge article per reviewed plan. It uses only the configured Machine actor, current People mappings, live schema/choices and active Knowledge base. Publication is controlled in the approved payload as Knowledge workflow_state (`Draft` or `Published`) at create time; no arbitrary table, audit-field spoofing, source user/role changes, checkout/revision, or existing-record updates. Requester incident descriptions stay first-person; audience-visible titles and bodies reject artificial-data labels. Knowledge HTML is limited to simple structural tags without attributes.

Use `ContentPreview -Name '<selected config>' -InputFile '<normalized nonsecret JSON>'`, or `/api/content/preview` with `profileId`, `expectedRevision` and `input`. The input is `{businessKey, incident?, knowledge?}`. Incident fields: short_description, description, caller_id and optional category/impact/urgency. Knowledge fields: short_description, text, author, kb_knowledge_base, optional `publish` (default `true`; set `false` for Draft). Do not copy pack-level internal metadata into source text. The controller adds technical owned IDs/tracking and validates configured Human references, the author's existing Knowledge role, field types/limits, installed choices and exact title/owned-ID duplicate lookups. Source ACLs may still deny a write despite readable schema.

After exact user consent, `ContentApprove -PlanId '<id>' -PlanHash '<hash>' -Confirm`, then `ContentApply` with that ID/hash. Equivalent authenticated API routes are `/api/content/approve` and `/api/content/apply`. `ContentStatus` and `/api/content/status` read persistent state. Approval binds the exact selected config/revision, PDI, actor and payload, and expires after 30 minutes. Use the existing no-redundant-confirmation rule when the same exact content was already reviewed and approved in chat.

Every source POST has a durable attempting step before dispatch. Incident uses its owned primary ID and correlation_id; Knowledge uses its owned primary ID. Read-back requires exact source ID, returned number, real sys_created_by actor and approved fields/HTML/reference values. A title alone never permits adopting or editing someone else's record. `ContentReconcile` / `/api/content/reconcile` is read-only and can confirm only exact attempted owned records; it never re-POSTs. Remaining unattempted steps require renewed exact approval. New previews cannot bypass unresolved attempts on the same PDI. A stable businessKey returns the same confirmed results for unchanged inputs instead of duplicating records; changed source content or inputs blocks for inspection.

**Checkout/revision and source content updates remain separate, unfinished capabilities.** The engine can create new Knowledge records in Draft or Published state when explicitly approved, but it cannot PATCH an existing article, run Checkout/revision flows, bypass workflow/ACL, or imply Copilot ingestion. Preserve the chosen author and use the normal source lifecycle for post-create edits and revisioning. General batch reseeding/cleanup and connector deployment remain out of scope.
